# Rust feature support chart

What compiles today, by area, and how each feature is lowered to JS. **Status**: ✅ done · 🚧 in progress ·
⬜ planned · ❌ won't support · ⚠️ supported with a documented gap (see `RUST_GAPS.md`). A ✅ or ⬜ inside
a row marks one part of it. Open work is in `PLAN.md`.

## Items and modules

| Feature | Status | JS lowering / notes |
|---|---|---|
| `fn` items, params, return types | ✅ | `function`; all top-level fns exported (like RapydScript `export_all`). Parameters may be patterns (`(r, c): (usize, usize)`, `Point { x, y }: Point`, `&(a, _)`), also in methods |
| `async fn`, `.await` | ✅ | `async function`, `await` |
| `async { .. }` / `async move { .. }` blocks | ✅ | A future of the block's value (`.await` inside, `?` and `return` leave the block): an async arrow function called at once, so it starts running where it's written (a Rust future waits to be polled) |
| Async closures (`async \|x\| ..`, `async move \|x\| ..`) | ✅ | An async arrow function: calling it gives a future of the body's value (`.await`, `?` and `-> T` inside). `F: AsyncFn(A) -> R` (and `AsyncFnMut` / `AsyncFnOnce`) and `F: Fn(A) -> Fut, Fut: Future<Output = R>` parameters take them. Like `async` blocks they start running when called. `F: Future<Output = T>` parameters (with `T` another type parameter too) and a bare `F: Future` (its `F::Output`) take any future, `.await`ed in the body |
| `Pin<Box<dyn Future<Output = T>>>`, `Box::pin(fut)` | ✅ | The future itself (`Pin` and `Box` are erased), so recursive async functions work: `fn walk(..) -> Pin<Box<dyn Future<Output = usize> + '_>> { Box::pin(async move { .. walk(..).await .. }) }`. `impl Future<Output = T>` return types too |
| Hand-written futures (`impl Future for X`) | ✅ | `type Output = T; fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<T>` with `std::task::{Context, Poll, Waker}` (a Rust-source prelude: `Poll::Ready` / `Pending`, `is_ready`, `map`; `cx.waker()`, `wake` / `wake_by_ref` / `clone`, `Waker::noop()`, `Context::from_waker`), `Pin::new(&mut x)`, `Box::pin`, `pin!`, `as_mut()`, `get_mut()` (all erased); a future polling another one (hand-written, boxed, an `F: Future` field or an async fn's); `std::future::{ready, pending, poll_fn}`. `.await` on one (or passing it as an `F: Future` / `impl Future`) polls it from the runtime, waiting for its waker after each `Pending`; your own executor (`block_on` with a no-op waker) polls hand-written futures as in Rust. Diff-tested against rustc |
| `impl Drop for T` | ✅ | `drop` runs when a value goes out of scope (block end, `return`, `break`, `?`, a panic), in reverse declaration order; a moved value is dropped by its new owner (a flag per binding); `drop(x)` / `mem::drop(x)` drop at once, reassigning drops the old value, `let _ = make()` and `make();` drop the temporary, by-value parameters drop at the end of the function, and `self` at the end of a method taking it by value (unless moved on); a closure owns the values it captures by value (`move`, or moved in its body), which drop with it: when its binding ends, when the function it was passed to ends, or with the struct, `Box` or `Vec` holding it; fields drop after their owner's `drop`, in order, and `Vec` / `Option` / map elements too. Diff-tested against rustc |
| `fn main()` / `async fn main()` | ✅ | `export function main()` / `export async function main()`, the module's entry point, which the host calls; `-> Result<(), E>` too (see "`std::error::Error`") |
| `const`, `static` | ✅ | Module-level `export const`s, emitted after the classes in dependency order (any declaration order works); usable in patterns and as range bounds (`0..=LIMIT`), as are associated consts (`Self::MAX`, `S::ZERO`, `<S as Tr>::TOP`, `S::LO..=S::HI`) and std ones (`u8::MAX`); integer values count for exhaustiveness. `static mut` is a module-level `let`; using it outside `unsafe` is an error like rustc's, as is assigning to a plain `static` |
| `struct` (named, tuple, unit) | ✅ | A JS `class` whose constructor takes the fields in order; tuple fields are `this[0]`. Literals with shorthand and `..base`, field access and assignment, struct patterns. Generic structs: see below |
| `impl` blocks (inherent) | ✅ | Class methods (`self` is `this`); associated functions are `static`. `&self` / `&mut self` / `self`, `Self`, `Self { .. }`, UFCS `Point::len(&p)`, methods and constructors as function values. | `enum` (field-less) | ✅ | Same class as data enums; `as i32` honours explicit discriminants, which may be constant expressions (`A = BASE + 1`, `B = 1 << 3`, `C = Other::X as isize`, `u8::MAX`, `b'a'`, with implicit increments after them) |

## JS globals (from RapydScript)

RapydScript-NG (`~/work/rapydscript-n`) gives its scripts the browser and JS globals, and its
language service declares them for hover and completion
(`src/monaco-language-service/js-globals-dts.js`). CarciniScript reaches them through the
built-in `js` crate, declared in `bindings/js.rs` in the format every bindings file uses (extern
types with typed fields and methods, plus `#[getter]`, `#[array]`, `#[optional]`, `#[variadic]`,
`async fn`, associated functions such as `Date::now()`, and free functions such as
`js::set_timeout(..)`, also imported by name: `use js::{btoa, set_timeout};`). Closure
parameters (`impl Fn(Event)`) take Rust closures directly. Assigning a field
(`el.inner_html = ..`) needs a `let mut` binding, as in Rust.

Tests: `test/js/` (Date, JSON) against native stand-ins and serde_json; `test/js-node/` (Math,
performance, crypto, base64, URLs, globals, timers, `Promise::all` / `race`) under Node against
expected output; the DOM, storage, window, location and navigator in a real browser
(`tools/browser-check.mjs`).
